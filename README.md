# Workshop Booking System

Учебный REST API для бронирования мастер-классов на Django и Django REST
Framework. Пользователь может зарегистрироваться, посмотреть мастер-классы,
записаться, перенести или отменить свою бронь. Администратор управляет
мастер-классами.

## Стек

- Python 3.12+, Django 6.0, Django REST Framework.
- PostgreSQL (в Docker — версия 16).
- Simple JWT: вход по email и паролю.
- drf-spectacular: Swagger UI и ReDoc.
- Postman: запросы и автотесты.

## Запуск через Docker

Нужны Docker Desktop с работающим Linux-движком и Docker Compose.

1. Клонируйте репозиторий и перейдите в его папку.
2. Создайте файл настроек.

   PowerShell:

   ```powershell
   Copy-Item .env.example .env
   ```

   Linux / macOS:

   ```bash
   cp .env.example .env
   ```

3. В `.env` задайте свой `DJANGO_SECRET_KEY` и пароль PostgreSQL.
   Остальные значения подходят для локального запуска.
4. Соберите и запустите проект:

   ```bash
   docker compose up --build -d
   ```

   После проверки готовности PostgreSQL Django применяет миграции и
   запускается на порту 8000. Для учебной демонстрации используется сервер
   разработки Django.

Откройте [Swagger UI](http://localhost:8000/api/schema/swagger-ui/).

Полезные команды:

```bash
docker compose logs -f web
docker compose exec web poetry run python manage.py test workshops
docker compose down
```

Данные PostgreSQL хранятся в томе `postgres_data` и сохраняются после
`docker compose down`. Параметр `-v` удаляет том вместе с БД.

Если порт PostgreSQL 5432 занят, поменяйте `POSTGRES_PORT` в `.env`.
Внутри Docker Django обращается к сервису `db` на порту 5432.

## Локальный запуск Django

Нужны Python 3.12 или новее и Poetry 2.x.

1. Проверьте, что Poetry установлен:

   ```bash
   poetry --version
   ```

2. Установите основные зависимости и инструменты разработки:

   ```bash
   poetry install
   ```

   Poetry создаст отдельное виртуальное окружение проекта и установит
   точные версии из `poetry.lock`.

3. Скопируйте `.env.example` в `.env`, как описано выше.
4. Запустите только PostgreSQL в Docker:

   ```bash
   docker compose up -d db
   ```

   Можно использовать и установленный PostgreSQL. Создайте отдельные базу
   и пользователя, затем укажите их параметры в `.env`. Пример SQL
   для локального учебного окружения:

   ```sql
   CREATE USER workshop_user WITH PASSWORD 'workshop_password' CREATEDB;
   CREATE DATABASE workshop_booking OWNER workshop_user;
   ```

   Замените пароль и укажите такой же в `.env`. Право `CREATEDB` нужно
   для тестов: Django создаёт и удаляет отдельную тестовую базу.

5. Примените миграции и запустите Django:

   ```bash
   poetry run python manage.py migrate
   poetry run python manage.py runserver
   ```

API: [http://localhost:8000/api/](http://localhost:8000/api/).

## Демонстрационные данные

При первом выполнении `python manage.py migrate` миграция создаёт четыре
будущих мастер-класса, четыре брони и следующие учётные записи:

| Роль API      | Username | Email               | Пароль  |
| ------------- | -------- | ------------------- | ------- |
| Администратор | `admin`  | `admin@example.com` | `admin` |
| Пользователь  | `user`   | `user@example.com`  | `user`  |
| Пользователь  | `user2`  | `user2@example.com` | `user2` |

Начальные мастер-классы: «Создание REST API на Django», «Основы публичных
выступлений», «Мобильная фотография» и «Эффективное управление временем».

В REST API вход выполняется по email и паролю. Поэтому для входа
администратором используйте `admin@example.com` и `admin`.

Учётная запись `admin` имеет роль администратора API и может управлять
мастер-классами, но не является суперпользователем Django. Если нужен доступ
к служебной панели `/admin/`, отдельно выполните
`poetry run python manage.py createsuperuser`. Созданный этой командой
пользователь получит полные права
Django, а поле `role` останется равным `user`. Доступ к операциям
администратора API сохранится благодаря флагу суперпользователя.

Эти простые пароли предназначены только для локальной демонстрации. В
опубликованном приложении демонстрационную миграцию следует удалить или
заменить безопасным способом создания первого администратора.

## Настройки окружения

| Переменная             | Назначение                                       |
| ---------------------- | ------------------------------------------------ |
| `DJANGO_SECRET_KEY`    | Ключ Django и подписи JWT                        |
| `DJANGO_DEBUG`         | Режим отладки, `True` для локальной демонстрации |
| `DJANGO_ALLOWED_HOSTS` | Разрешённые имена хостов через запятую           |
| `POSTGRES_DB`          | Имя базы                                         |
| `POSTGRES_USER`        | Пользователь базы                                |
| `POSTGRES_PASSWORD`    | Пароль базы                                      |

| `POSTGRES_PORT`        | Порт PostgreSQL на компьютере                    |

Файл `.env` не добавляется в Git. Перед размещением на сервере используйте
собственные ключ и пароль, отключите DEBUG и настройте разрешённые хосты.

## REST API

| Метод      | Адрес                  | Доступ и назначение                                |
| ---------- | ---------------------- | -------------------------------------------------- |
| POST       | `/api/register/`       | Регистрация обычного пользователя                  |
| POST       | `/api/token/`          | Вход по email и паролю, получение access и refresh |
| POST       | `/api/token/refresh/`  | Обновление access по refresh                       |
| GET        | `/api/workshops/`      | Публичный список мастер-классов                    |
| GET        | `/api/workshops/{id}/` | Публичные детали мастер-класса                     |
| POST       | `/api/workshops/`      | Администратор: создание                            |
| PUT, PATCH | `/api/workshops/{id}/` | Администратор: полное или частичное изменение      |
| DELETE     | `/api/workshops/{id}/` | Администратор: удаление вместе с бронями           |
| GET        | `/api/bookings/`       | Свои бронирования                                  |
| GET        | `/api/bookings/{id}/`  | Детали своей брони с мастер-классом                |
| POST       | `/api/bookings/`       | Запись на мастер-класс                             |
| PUT, PATCH | `/api/bookings/{id}/`  | Перенос своей брони                                |
| DELETE     | `/api/bookings/{id}/`  | Отмена своей брони                                 |

Все операции с бронями требуют авторизации:

```http
Authorization: Bearer <access_token>
```

Регистрация:

```json
{
  "email": "student@example.com",
  "username": "student",
  "password": "studentPass"
}
```

Вход:

```json
{
  "email": "student@example.com",
  "password": "studentPass"
}
```

Создание или перенос брони:

```json
{
  "workshop_id": 1
}
```

Для мастер-класса нужны `title`, `description`, `date` в ISO 8601
и `capacity`. Выбирайте будущую дату для демонстрации бронирования.
Сервер хранит дату и время в UTC. Передавайте часовой пояс в значении
`date`, например `2030-01-10T18:00:00+03:00` или
`2030-01-10T15:00:00Z`. Клиент при необходимости преобразует полученное
время в часовой пояс пользователя.

Списки содержат `count`, `next`, `previous`, `results`.
На странице до 10 записей; следующая страница — `?page=2`.

## Правила бронирования

- Один пользователь может иметь только одну бронь на мастер-класс.
- Название каждого мастер-класса должно быть уникальным.
- На прошедший мастер-класс записаться нельзя.
- При отсутствии мест API возвращает ошибку 400.
- Проверка мест и сохранение выполняются в одной транзакции.
  PostgreSQL блокирует строку мастер-класса через `select_for_update`,
  поэтому два запроса не могут одновременно занять последнее место.
- Перенос освобождает старое место только после проверки нового.
- Повторный PUT с тем же мастер-классом и пустой PATCH сохраняют бронь.
- Вместимость нельзя уменьшить ниже числа действующих броней.
- Чужая бронь отсутствует в списке и возвращает 404 при обращении по ID.
- Пароли хешируются и не возвращаются в ответах API.

В `/admin/` можно управлять пользователями и назначать роли.
Мастер-классы и бронирования доступны там для просмотра; изменяются они
через REST API с проверкой бизнес-правил. Суперпользователи имеют права
администратора API независимо от значения поля `role`.

## Postman

Файлы для импорта:

- [Коллекция запросов](postman/Workshop.postman_collection.json)
- [Локальное окружение](postman/Local.postman_environment.json)

Порядок запуска:

1. Примените миграции: они создадут демонстрационного администратора.
2. Импортируйте оба файла и выберите окружение **Workshop Local**.
3. Проверьте `base_url`. Данные администратора уже записаны в окружении.
4. Запустите всю коллекцию через **Run collection** в исходном порядке.

Коллекция содержит 56 запросов: регистрацию, JWT, все операции мастер-классов
и бронирований, документацию, проверки прав, дублей, даты и вместимости.
Для каждого запроса проверяется код ответа; дополнительно проверяются
формат JSON, владелец брони и вложенные данные.

Имена пользователей и даты создаются перед первым запросом.
Токены и ID сохраняются в переменных коллекции автоматически.
После успешного прогона созданные мастер-классы и брони удаляются.
Два тестовых пользователя остаются в БД; используйте учебную базу.

Для запуска из терминала с установленным Node.js:

```bash
npx newman@6.2.1 run postman/Workshop.postman_collection.json -e postman/Local.postman_environment.json
```

## Проверки

```bash
poetry run python manage.py test workshops
poetry run python manage.py check
poetry run python manage.py makemigrations --check --dry-run
```

Тесты работают на отдельной базе PostgreSQL. Проверяются основные сценарии
и одновременные запросы на последнее место. Рабочая база не очищается.

Проверка оформления кода:

```bash
poetry run pycodestyle --exclude=migrations workshops workshop_booking manage.py
```

Автоматически сгенерированные миграции исключены из проверки длины строк.
